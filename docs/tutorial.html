The big picture

A yearly LLM bill is just one multiplication chain. The hard part is that every term in it is usually a guess. The estimator pins down each term with a concrete, inspectable input:

# annual cost is the product of four grounded quantities annual_cost = users × conversations_per_user_per_year × tokens_per_conversation ← from YOUR samples × price_per_token ← Azure Data Zone list price × engagement_multiplier ← per user-segment weighting

The four numbered sections of the app each nail down one part of that chain. The rest of this tutorial walks them in order.

Pick the model (each carries its Azure Data Zone input/output price per million tokens) and the number of users per year. These set price_per_token and users.

2

Engagement distribution

Real user bases are not uniform: a handful of power users can dwarf everyone else. Instead of one "average user," you choose a distribution that splits your population into segments, each with a share of users and a usage multiplier. The app allocates whole users to each segment and computes a weighted multiplier for the whole base.

Four presets ship in src/lib/distributions.ts (mostly-quiet, balanced, power-user-heavy, chatty long-tail). Shares always sum to 100%, and users are allocated with a largest-remainder method so the segment counts stay integer-exact.

Each preset is a selectable card with a mini histogram. In every bar, width = share of users and height = engagement multiplier (√-scaled so a 25× outlier doesn't flatten the rest). Because width × height = area, each bar's area ≈ that segment's share of tokens — so the skinny-but-tall power-user spike visually is its outsized cost. A dashed 1× line marks average engagement.

Conversation workflows

A conversation is rarely a single API call. You compose each flow from stages in a visual designer — add, remove, and reorder them — so the token count matches how your pipeline actually runs. Four stage types are available:

  1. Opening — the assistant sends the first message (assistant-first flows).
  2. Gate — a cheap classifier decides whether to engage (engageRate). It's the only stage that branches: everything after it is scaled to that fraction of conversations.
  3. Answer → Judge — one coupled stage. The model drafts a reply, an LLM-as-judge grades it, and on a fail the loop repeats up to maxAnswerAttempts times.
  4. LLM call — a generic single call (prompt → response) for any ad-hoc step.

The shared user message is a flow-level input every gate / answer / judge call sees, counted once and reused. Two presets seed a default stage list — user-first = [gate, answer→judge] and assistant-first = [opening, gate, answer→judge] — and the moment you hand-edit the stages the preset flips to Custom.

4

From sample messages to tokens

This is the heart of the tool. Each stage block in the pipeline has its own sample fields. Paste text (one sample per line) or a JSON transcript, or upload a file. The badge on each field shows how many samples were parsed. Prompt fields marked (template only) want the prompt scaffolding without the user message or draft answer pasted in — those are counted separately, so including them double-counts.

How parsing works

Plain text

Split into one sample per non-empty line. Blank and whitespace-only lines are dropped before counting.

JSON transcripts

Arrays/objects are flattened by pulling text from known keys (content, text, prompt, …). Envelope fields like role and id are ignored, so structure never inflates the token count.

Real tokenizer, not an estimate. Tokens are counted with js-tiktoken using the o200k_base encoding — the exact tokenizer used by OpenAI's GPT-4o → GPT-5 and o-series models. The app averages tokens across your samples per stage, then hands those averages to the workflow model.

Press Estimate workflow and the per-conversation token averages update from your samples. From there the rate knobs (engage rate, judge pass rate, max attempts) scale the input/output figures live — move a slider and the annual estimate follows instantly, no re-estimation needed.

The math, worked end to end

Because the answer→judge loop retries, "calls per conversation" is not a whole number. The expected number of answer attempts when engaged follows a truncated geometric expectation:

E[attempts] = ( 1 − (1 − passRate)^maxAttempts ) / passRate # e.g. passRate = 0.5, maxAttempts = 3 = ( 1 − 0.5³ ) / 0.5 = 1.75 attempts

Here is a fully worked, hand-checkable example for the user-first preset — a [gate, answer→judge] stage list. The engine folds over the stages tracking a reach probability: the gate runs once at reach 1, then scales the reach to engageRate for everything downstream. Assume these per-sample token averages and rates (small numbers chosen so you can follow along):

engageRate = 0.5 passRate = 0.5 maxAttempts = 3 → reach after gate = 0.5 → answer & judge calls = 0.5 × 1.75 = 0.875

Modeling assumption — input is an upper bound. The shared user message is counted as fresh input on every gate, answer, and judge call. Cached-input pricing is intentionally excluded, so real input cost can come in lower.
One more multiplier — API reliability. A global factor accounts for transport-level call failures (timeouts, 5xx, rate limits) that get retried. It's the same truncated-geometric overhead, applied to the input total only (a failed call rarely bills for output). The default — 99% success / 3 attempts ≈ 1.01× — is a rounding-error nudge; set success to 100% to switch it off.

The stage fold lives in combineFlowStages (src/lib/conversationWorkflow.ts) and is covered by unit tests, including equivalence tests proving the two presets reproduce the original fixed-pipeline numbers exactly.

5

Reading the live estimate

The right-hand panel updates on every keystroke. Per-conversation tokens are multiplied by conversations-per-user, by users, and by each segment's engagement multiplier, then priced — giving annual input, output, and total cost plus a per-segment breakdown.

Everything is live and local. There is no backend and no network call — change a price, a rate, or a sample and the whole chain recomputes instantly in your browser.

Try it yourself

  1. Start the app: bun run dev (or npm run dev), then open the printed URL.
  2. Expand a flow → load files into each stage block from the samples/ folder (see samples/README.md for the mapping).
  3. Click Estimate workflow, then drag the rate knobs and watch the right-hand panel update live.
  4. Swap the model, the distribution, and the user count to see the budget move.
