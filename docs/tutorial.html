The big picture

A yearly LLM bill is just one multiplication chain. The hard part is that every term in it is usually a guess. The estimator pins down each term with a concrete, inspectable input:

# annual cost is the product of four grounded quantities annual_cost = users × conversations_per_user_per_year × tokens_per_conversation ← from YOUR samples × price_per_token ← Azure Data Zone list price × engagement_multiplier ← per user-segment weighting

The four numbered sections of the app each nail down one part of that chain. The rest of this tutorial walks them in order.

1

Core assumptions

Pick the model (each carries its Azure Data Zone input/output price per million tokens) and the number of users per year. These set price_per_token and users.

GPT-5.5 → GPT-4o family o3 / o4-mini reasoning models $ per-million input & output pricing
Prices are list values baked into the app (src/lib/models.ts). Cross-check the live Azure pricing page before quoting a figure to anyone.
2

Engagement distribution

Real user bases are not uniform: a handful of power users can dwarf everyone else. Instead of one "average user," you choose a distribution that splits your population into segments, each with a share of users and a usage multiplier. The app allocates whole users to each segment and computes a weighted multiplier for the whole base.

Four presets ship in src/lib/distributions.ts (mostly-quiet, balanced, power-user-heavy, chatty long-tail). Shares always sum to 100%, and users are allocated with a largest-remainder method so the segment counts stay integer-exact.

3

Conversation workflows

A conversation is rarely a single API call. The app models it as a pipeline with a gate and a retry loop — the part that makes token counts realistic:

  1. Trigger — a user message arrives (or, for an assistant-first flow, the model generates an opening message first).
  2. Gate — a cheap classifier decides whether to engage at all (engageRate). Out-of-scope messages stop here.
  3. Answer — the model drafts a reply.
  4. Judge — an LLM-as-judge grades it. On a fail, the answer→judge loop repeats up to maxAnswerAttempts times.
4

From sample messages to tokens

This is the heart of the tool. Under Token Estimation Samples, each stage of the pipeline has a field. Paste text (one sample per line) or a JSON transcript, or upload a file. The badge on each field shows how many samples were parsed.

How parsing works

Plain text

Split into one sample per non-empty line. Blank and whitespace-only lines are dropped before counting.

JSON transcripts

Arrays/objects are flattened by pulling text from known keys (content, text, prompt, …). Envelope fields like role and id are ignored, so structure never inflates the token count.

Real tokenizer, not an estimate. Tokens are counted with js-tiktoken using the o200k_base encoding — the exact tokenizer used by OpenAI's GPT-4o → GPT-5 and o-series models. The app averages tokens across your samples per stage, then hands those averages to the workflow model.

Press Estimate workflow and the per-conversation input/output token figures update from your samples, ready to roll up into the annual estimate.

The math, worked end to end

Because the answer→judge loop retries, "calls per conversation" is not a whole number. The expected number of answer attempts when engaged follows a truncated geometric expectation:

E[attempts] = ( 1 − (1 − passRate)^maxAttempts ) / passRate # e.g. passRate = 0.5, maxAttempts = 3 = ( 1 − 0.5³ ) / 0.5 = 1.75 attempts

Here is a fully worked, hand-checkable example. Assume these per-sample token averages and rates (small numbers chosen so you can follow along):

engageRate = 0.5 passRate = 0.5 maxAttempts = 3 → answer & judge calls = 0.5 × 1.75 = 0.875

5

Reading the live estimate

The right-hand panel updates on every keystroke. Per-conversation tokens are multiplied by conversations-per-user, by users, and by each segment's engagement multiplier, then priced — giving annual input, output, and total cost plus a per-segment breakdown.

Everything is live and local. There is no backend and no network call — change a price, a rate, or a sample and the whole chain recomputes instantly in your browser.

Try it yourself

  1. Start the app: bun run dev (or npm run dev), then open the printed URL.
  2. Expand a flow → open Token Estimation Samples → load files from the samples/ folder (see samples/README.md for the mapping).
  3. Click Estimate workflow, then watch the right-hand panel update.
  4. Swap the model, the distribution, and the user count to see the budget move.
